## 1 · REPOSITORY / SYSTEM ARCHITECTURE
**Evaluated.** (a) *Inside the GFOF repo*: every instrument filing would redeploy galacticfederation.co (deployment risk), the evidentiary git history would be interleaved with marketing-site churn (verification noise), and authority separation would be nil — a GFOF site compromise or bad deploy could touch record paths. Rejected. (b) *Hybrid shared-Federation mono-repo*: same coupling objections at larger scale, and it would put Dossier and FCC history under one authority surface — against the firewall's spirit. Rejected. (c) **Separate FCC repository — RATIFIED (D-1): `fcc-record`, public GitHub primary, with separate FCC-scoped automation credentials — no reuse of broad GFOF/Dossier deployment credentials anywhere in the FCC pipeline** containing `/governance` (frozen docs imported with hash verification at genesis, Source Registry, benchmark menu, Standing Adversary Procedure versions), `/record` (instruments, filing log, corrections, receipts, identities, OTS proofs — append-only, CI-guarded), `/tools` (lock pipeline, verifier, aggregates builder), `/site` (empty until the separately-gated build), `/tests`.
**Defense.** Separation of authority: FCC's record has its own commit history, its own protections, its own deploy — no GFOF/Dossier credential or pipeline can touch it, and vice versa. Deployment risk: record commits never redeploy other properties; site deploys (later) render projections and cannot rewrite record paths (§19 CI guard). Independent verification: a verifier clones exactly one small repo containing only evidence and specs — the audit surface is minimal and self-contained. Public history: the repo's commit stream *is* the Layer-1 publication channel and stays clean enough to read. Future scalability: Stage 0.5/1 add record classes without touching other properties. Shared Federation OS assets: consumed by copy at site-build time (the proven dossier-site pattern) — sharing never forces co-location. Firewall: Dossier and FCC remain separate repositories, separate logs, separate deploys; cross-references are public URLs only. Genesis commit records the three frozen hashes, making the baseline itself part of the public history.

## 2 · PUBLIC RECORD STORAGE MODEL
**Hybrid: immutable artifacts + append-only event log + derived projections — RECOMMENDED** over one-JSON-per-instrument (mutating one file per state change makes diffs noisy and history-tampering easier to miss) and over pure event-sourcing (locked bytes deserve to exist as standalone verifiable files).
Per instrument, a directory `record/instruments/{instrument_id}/`:
`locked.json` — the exact RFC 8785 canonical bytes that were hashed. Written once, never modified (CI-enforced).
`events.ndjson` — append-only, one JSON event per line: `filed-locked`, `published`, `witness-degraded`, `witness-completed`, `anchor-requested`, `anchor-confirmed`, `annex-added`, `state-transition`, `challenge-received`, `resolution-recorded` (intent registration lives in the Filing Log's own chain, since it precedes the instrument's existence). Every event carries `{event_id (ULID), type, at, payload_refs, prev_event_sha256, event_sha256}`.
**Event hash-chain law (normative).** `event_sha256 = SHA256( RFC8785( event object with the event_sha256 field removed ) )`, with `prev_event_sha256` *inside* the canonicalized object. The NDJSON newline is transport/storage framing only — it is never part of the semantic hash. **Genesis rules:** an instrument chain's first event (`filed-locked`) sets `prev_event_sha256 = lock_sha256`, rooting the entire chain in the locked bytes; repo-level logs (Filing Log, corrections, receipts) root their first entry at `prev_event_sha256 = "0" × 64`. **Verifier procedure per line:** parse the JSON object → remove `event_sha256` → RFC 8785 canonicalize → SHA-256 → compare to the recorded `event_sha256` → confirm `prev_event_sha256` equals the prior line's `event_sha256` (or the chain root) → any mismatch, insertion, deletion, or reorder breaks every subsequent hash. Both canonicalization implementations (§3) hash every event; CI requires their agreement.
**Byte-preservation policy (repository law).** Cryptographic artifacts whose *bytes* are authoritative — every `locked.json`, every annex file, every `.ots` proof, every snapshot archive — are protected from Git working-tree transformations by an explicit `.gitattributes` strategy (`record/** -text`, `*.ots binary`) committed at genesis, and verification tooling reads raw blob bytes (`git cat-file`), never the working tree. NDJSON log files are covered by the same `.gitattributes` protection for hygiene, but their semantic integrity rests on the per-object RFC 8785 hash chain above, not on file bytes — framing corruption is detectable and repairable without evidentiary loss. A CI job checks out the repository on Linux, macOS, and Windows runners and verifies byte equality of every byte-exact artifact against its recorded hash — cross-environment preservation is tested, not assumed.
`annexes/{seq}-{type}.json` — immutable annex files (the nine frozen types), each hashed; events reference them.
`ots/` — proof files for this instrument.
Repo-level: `record/filing-log.ndjson` (§6), `record/corrections/fcc-corrections.ndjson` + periodic snapshot archives, `record/challenges/receipts.ndjson` (global receipt log — every submission, malformed included), `record/identities/{identity_id}.json` (registrations + explicit linking proofs only; reputation is NOT stored — it is a derived view recomputed from challenge history, which makes it impossible to hand-edit), `governance/` (Doctrine and Spec versions verbatim + Source Registry + benchmark menu + SAP versions, all versioned files, never edited in place), `derived/` (aggregates and projections, §14 — regenerated, labeled, never authoritative).
Git diffs are pure appends and new files; recomputation is a replay; hashing has fixed byte targets; history is preserved by construction.

## 3 · CANONICALIZATION / HASHING PIPELINE
Locked-body construction: operator tooling assembles the frozen field set; `filed_at` is written into the body at lock initiation as the pipeline's first act. Canonicalization: **two independent implementations run on every lock** — primary in the tooling's language, second in a different language/runtime (concretely proposed: a JS RFC 8785 implementation and a Python RFC 8785 implementation; library selection = ratification D-6) — both produce bytes; the pipeline requires byte-for-byte equality AND equal SHA-256 before proceeding. **No instrument may enter FILED/LOCKED if the canonical bytes cannot be independently reproduced — enforced as a hard pipeline gate, not a policy.** Irrevocability — **the COMMIT POINT (Correction 1):** DRAFT → FILED/LOCKED occurs at **the first successful independently observable publication of the final `lock_sha256` through an approved Layer-1 witness.** From that instant the instrument can never return to DRAFT and the locked bytes can never change — full rules in §4. Failure behavior before any witness succeeds: canonicalization mismatch, hash mismatch, schema failure, or lint failure → abort, event logged locally, DRAFT retained; nothing independently observable exists, so nothing is locked.

## 4 · PUBLICATION + PRECEDENCE (frozen three-layer model)
Layer 0 · SELF-REPORTED: `filed_at`, `requested_at` — recorded, rendered as claims, never as proof.
Layer 1 · PUBLISHED — **multi-witness publication with one deterministic COMMIT POINT (Correction 1).** Approved Stage-0 witnesses: (w1) git push of `locked.json` + events to the public `fcc-record` repository (host-attested); (w2) an automated post of `{instrument_id, lock_sha256}` to the existing Federation public Telegram channel, speaking as the parent Federation until a separate FCC public identity is authorized (RATIFIED D-2), always labeled attestation-grade. The witnesses are two external systems and are **not atomic** — so the state transition is defined by one rule: **the FIRST successful independently observable publication of the final `lock_sha256` through an approved witness IS the commit point; DRAFT → FILED/LOCKED occurs at that instant, irrevocably.** The four cases:
— **Both succeed:** the commit point is the earlier success; both references recorded in `publication_ref`.
— **Git succeeds, second witness fails:** FILED/LOCKED at the git publication. The witness failure is *publication degradation*: a `witness-degraded` event is logged, retries proceed, telemetry exposes the degraded state, and a `witness-completed` event closes it. The locked body is never changed or reissued.
— **Second witness succeeds, git fails:** FILED/LOCKED at the witness publication instant. The instrument is locked even though the repository temporarily lacks it; repository publication is retried, telemetry shows the pending repo state, and on recovery the commit includes the witness's `publication_ref` and timestamp. The lock's existence never depends on the repo catching up.
— **Neither succeeds:** nothing became independently observable → the instrument remains DRAFT; retry or discard freely.
**Binding rule:** the pair `(instrument_id, lock_sha256)` becomes permanent at the commit point. Publishing a different hash for the same instrument id is prohibited; if it ever occurs (bug, race, compromise), the **earliest publication wins** — it defines the locked body; the later publication is an integrity incident requiring a corrections entry, and if the earliest-published bytes cannot be produced intact, the instrument terminates INVALIDATED-BY-DOCTRINE. A publication whose success is uncertain (sent, no confirmation) is treated as possibly-published: the pipeline must reconcile before any further publication for that id, and never issues a second hash while unresolved. No new state is added to the frozen state machine — these rules define the entry condition of FILED/LOCKED, nothing more. Every rendering labels Layer 1 **host/witness-attested — not cryptographic proof**; the architecture never lets a Git or Telegram timestamp masquerade as cryptography.
Layer 2 · ANCHORED: OTS/Bitcoin per §5 — the only layer rendered as cryptographic, and only for what it proves: an upper bound (`anchor_blocktime`).
`ordering_evidence` is computed exactly per the frozen Spec §3.4–3.6, including the permanent "PRECEDENCE: NOT INDEPENDENTLY PROVEN" rendering and the anchored-precedence share in aggregates. **Stage-1 precedence remains CLOSED; nothing here addresses it.**

## 5 · OTS INTEGRATION
Anchor request: `ots stamp` over `locked.json` immediately at lock (same pipeline run as publication); the incomplete proof file is committed to `ots/` and `anchor-requested` logged with `requested_at`. Pending state: envelope projection shows `anchor: pending`; `ordering_evidence.level` stays PUBLISHED. Confirmation: a scheduled job (and a manual command) runs `ots upgrade` + `ots verify` per pending proof; on Bitcoin attestation, the upgraded proof file is committed and `anchor-confirmed` logged with `anchor_blocktime` extracted from the attestation. Verification path: the proof file is downloadable from the repo; independent verification = OTS client against the verifier's own Bitcoin node (full trustlessness) or public calendars (documented as the lighter-trust mode). Re-anchor: fresh stamp over the same bytes; all proofs retained. Permanent failure: the frozen Spec §3.5 procedure verbatim — disclosure annex + corrections entry + re-anchor + permanent Layer-1 labeling for the affected interval. Frozen rule preserved mechanically: the resolution engine (§11) refuses TERMINAL while required anchor conditions are unmet.
**OTS failure after the commit point (Clarification 2).** The case: approved witness succeeds → COMMIT POINT reached → instrument irrevocably FILED/LOCKED → the initial OTS submission fails. Rule: **once the commit point has occurred, OTS failure can never return an instrument to DRAFT and can never permit altered or reissued locked bytes.** The instrument remains FILED/LOCKED — the state machine has no path backward and none is added. The condition is an **operational degradation, not an instrument state: `ANCHOR SUBMISSION DEGRADED`.** Behavior: the anchor request is retried over the exact same `locked.json` bytes; the degradation is exposed on the System/Telemetry surface; every failed and retried attempt is preserved as events in the instrument's hash-chained log (`anchor-requested` with failure payloads, per attempt); `lock_sha256` never changes; and TERMINAL remains blocked exactly per the frozen anchor requirements until a confirmation exists. Two causes are distinguished: **(A) submission failure attributable to FCC — tooling, configuration, or operator error** (the stamp was never validly attempted, or attempted so defectively it could not succeed): a procedure failure, recorded as a conduct-class violation event with corrections treatment, and therefore **capable of producing PROCESS = VIOLATED** under the frozen Doctrine's conduct-violation rules; **(B) a successful, timely submission followed only by external calendar or Bitcoin confirmation delay:** not a PROCESS violation by itself — the already-frozen pending/precedence rules govern, the instrument waits at `anchor: pending`, and `ordering_evidence` reports whatever layer is actually earned. The distinction is evidentiary and mechanical: the event log shows whether a well-formed submission left FCC's tooling on time.

## 6 · FILING LOG (Doctrine §F3)
`record/filing-log.ndjson`, append-only, one entry per assessment at the moment work begins — not at publication decision. Entry: `{filing_id (format D-6, e.g. FCC-F-0001), subject, rationale, opened_at, status: OPEN-WORK | FILED | ABANDONED, instrument_id (C, when filed), abandonment_reason (C, required when abandoned), proposal_source (C: proposal-queue reference where applicable), events[]}`. Status changes are appended events, never edits. Abandoned entries remain forever; the abandonment count is a first-class aggregate (§14). The proposal queue itself is a public file with published triage states, satisfying the R-9 mitigations.

## 7 · INSTRUMENT CREATION PIPELINE
REGISTER INTENT — human-initiated, tooling-logged (Filing Log append). → DRAFT — human. → EVIDENCE — human gathers; tooling content-hashes static documents and records live-source snapshots (automated assist). → CRITERIA — human authors; tooling validates machine-evaluability schema (**hard-blocking**). → SOURCE SELECTION — human selects; registry-membership check (**hard-blocking**). → CONFLICT DISCLOSURE — human-confirmed mandatory step; an empty conflicts array requires an explicit affirmative confirmation action (**hard-blocking** until confirmed). → AI LINT — automated (**hard-blocking** on: criteria determinism, evidence dependency coverage, benchmark-menu compliance, ordering satisfiability, §B eligibility including the $GFOF/Federation-asset exclusion, horizon ≥ 72h minimum OPEN); lint output preserved for publication with the instrument. → TRIVIALITY REVIEW — pre-lock adversarial probe records the §F4 triviality assessment; the authoritative TRIVIAL flag is set when the mandatory post-lock counter-thesis lands, per §B4 (two-step reading **RATIFIED, D-7**). → HUMAN REVIEW — owner sign-off (**hard-blocking**). → LOCK — automated pipeline per §3–§5, atomic to publication. **The system refuses LOCK if any frozen eligibility condition fails — refusal is the pipeline's default state; lock requires every gate green.**

## 8 · AI STANDING ADVERSARY (mandatory, never authoritative)
`governance/adversary/sap-vN.md` — the versioned Standing Adversary Procedure: procedure text, prompt template, required coverage checklist (the frozen counter-thesis check list), and the metadata schema. Changing it is a Doctrine §P amendment, prospective only. Every counter-thesis annex records vendor-neutral metadata: `{sap_version, model_vendor, model_identifier, model_version_string, generation_params, generated_at, input_sha256 (hash of the locked bytes provided)}` — enough to reproduce the conditions without binding FCC to any vendor. **RATIFIED (D-5): SAP v1 uses the high-reasoning Claude model available to the project, recording the exact vendor/model identifier and generation metadata returned by the environment — never a marketing/UI name; the vendor-neutral architecture remains mandatory and vendor swap remains a prospective SAP amendment.** Raw output is stored verbatim as the annex body; the annex hash covers it, so post-publication rewriting is detectable; corrections to a flawed counter-thesis happen by supplement annex, never by edit. Human adversarial supplements are a distinct annex type. Doctrine lint (§7) uses the same versioning discipline. **Architectural enforcement of the prohibitions:** the AI subsystem has no write path to `locked.json`, no ability to append state-transition events (those require the operator-signed pipeline), no publish credentials, no key material — it cannot lock, file, resolve, authorize, move capital, alter evidence, or rewrite its published output, because no code path exists by which it could.

## 9 · CHALLENGE SYSTEM
Flow: SUBMIT → PUBLIC RECEIPT → VALIDATE FORMAT → CONSOLIDATE DUPLICATES → PENDING → FCC RESPONSE → RESOLUTION → OPTIONAL META-CHALLENGE (one round) → FINAL.
Intake — **RATIFIED (D-3): primary structured FCC challenge endpoint + public GitHub issue-template fallback.** Operational abuse controls may throttle or queue but may never silently discard a well-formed challenge.
**Receipt durability (Correction 3) — two distinct receipt classes:**
— **PROVISIONAL RECEIPT:** the intake endpoint immediately returns a **signed** acknowledgement to the submitter: `{provisional_receipt_id (ULID), instrument_id, challenge_content_sha256 (RFC 8785 over the submission), received_at, intake_key_version, signature}` — signed with a dedicated FCC intake keypair whose public key (and every prior key version) is published under `governance/keys/`. The provisional receipt is durable at intake (persistent queue) and is **never discarded**, whatever happens next.
— **PUBLIC RECEIPT:** the append of the submission to `receipts.ndjson` pushed to the public repository — the independently observable publication with a public reference and timestamp. **A public challenge admission is complete only when the PUBLIC RECEIPT exists.**
If public publication fails after a provisional receipt is issued: the provisional receipt is retained, publication is retried from the durable queue, the pending/failed count is exposed on the System/Telemetry surface, and the challenge is never silently suppressed — suppression is not a code path. **Independent presentation:** the challenger can present their signed provisional receipt to anyone; verification against the published intake key proves FCC's system received the submission at `received_at`, and the absence of a matching public receipt is then publicly demonstrable evidence of intake failure or suppression, actionable as an FCC process violation and corrections entry. **First-filer ordering uses the provisional `received_at` where a validly signed provisional exists** (public-receipt time otherwise), so a publication delay can never reassign first-filer credit. These are intake states, not instrument states — the frozen state machine is untouched. The GitHub issue channel is inherently public at submission (issue permalink = provisional and public receipt in one), and its submissions are mirrored into `receipts.ndjson` for the unified log. Format validation: automated against the frozen challenge schema; malformed → status RETURNED-MALFORMED with published triage reason, receipt retained.
**The response clock (Clarification 1).** The frozen 7-calendar-day FCC response obligation is measured from exactly one time: for the structured endpoint, **the signed PROVISIONAL receipt's `received_at`, once the submission is determined to be a well-formed challenge.** The later PUBLIC receipt does not reset, restart, or extend the deadline — a delay in publishing the public receipt never buys FCC response time, because the deadline is `provisional received_at + 7 days` regardless of when publication lands. When the public receipt is published, it **includes the signed provisional receipt (or a verifiable reference to it)** — id, `received_at`, content hash, key version, signature — sufficient for any third party to verify the original intake time and independently recompute the deadline FCC was under. For the GitHub issue fallback, **the issue creation timestamp is the receipt time** — provisional and public observability occur in the same act, so there is nothing to separate. **Validation latency never moves the clock:** a submission later determined well-formed retains its original intake `received_at` as the clock's start — deliberately postponing format validation postpones nothing, since the determination is retroactive to intake; the only submissions with no response deadline are those finally classified RETURNED-MALFORMED, and even those keep their receipts and published triage reasons. First-filer ordering remains on the provisional `received_at`, as already ratified. Consolidation: operator tooling marks duplicates CONSOLIDATED with first-filer attribution by receipt timestamp. PENDING → FCC response within the frozen **7-calendar-day window**, measured mechanically from the receipt timestamp — the breach detector (§12) reads only public timestamps, so a breach cannot be hidden. Resolution: human (operator) applies the frozen §J per-category tests; AI may draft analysis as a labeled annex but never resolves. Meta-challenge: one round, then FINAL; unresolved dispute sets the DISPUTED flag. Frozen constraints preserved verbatim: eight categories, no token gate, wallet + account identities, separate reputations unless explicitly linked, one category per identity per instrument, first-filer credit. **Anti-spam lives at the operational intake layer only** — per-identity rate limits, payload size caps, format validation — never as an access gate: every well-formed challenge from any identity reaches PENDING, and even rejected payloads keep their receipts.

## 10 · IDENTITY + REPUTATION
`record/identities/{identity_id}.json`: `{identity_id, type: wallet | account, key_or_handle, registered_at, links: [{other_identity, wallet_signed_statement_ref, account_confirmation_ref, linked_at}]}`. Wallet identity = possession of the key, proven per submission by signature over the challenge's canonical bytes; account identity — **RATIFIED (D-4): passkey/WebAuthn architecture** for registered accounts, wallet identity remaining signature-based; separate reputation identities unless explicitly, verifiably linked, exactly as frozen. Linking is explicit and bidirectional (signed statement + account confirmation), per frozen S-3; the system never infers common ownership. Pseudonymity is native — no real-name requirement anywhere. **Reputation is a derived view** (§14): recomputed from the public challenge history (upheld / partially upheld / not-upheld counts, frivolous-pattern visibility), displayed with identity age and full history link; because it is derived, it cannot be granted, edited, transferred, purchased, or made to yield — those failure modes have no storage location to exist in. No token gate anywhere in the identity path.

## 11 · RESOLUTION ENGINE
Horizon detection: scheduled job lists OPEN instruments whose horizon has passed AND whose required anchor conditions are satisfied (else they wait, rendered honestly as pending). Named-source retrieval: per criterion, scripted retrieval from the locked primary source (fallback per the frozen rules when the primary is dead); the raw response is archived and hashed into the terminal-resolution annex, so the reading itself is later verifiable. Evaluation: mechanical execution of each locked `evaluation_procedure` (automated). Challenge resolution: human, per §9. Benchmark results: mechanical from the locked menu selections where applicable (automated). Disposition, OUTCOME, PROCESS, informational outcome, DISPUTED flag: derived by rule from the frozen mappings (automated computation), with the terminal state-transition event **operator-signed** — automation computes, the human confirms, and the record shows both the computation and the confirmation. Everything the engine consumed is public (locked bodies, archived readings, annexes, receipts), so the final result is independently recomputable end to end — the verifier (§15) re-derives it.

## 12 · PROCESS-SCORING ENGINE
Detectors, all reading only public artifacts: late response — provisional `received_at` (or issue creation time on the fallback channel) vs fcc-response annex timestamp > 7 calendar days (automated, unhideable; public-receipt publication time is irrelevant to the computation by Clarification 1); ordering defects — anchor_blocktime / publication / horizon comparisons (automated); disclosure failures — surfaced by challenge or self-disclosure, encoded as violation events (human-triggered, permanently recorded); benchmark violations — post-hoc menu-compliance recomputation (automated) in addition to pre-lock lint; evidence defects — via evidence-defect disclosure annexes + corrections entries; annex-integrity failures — hash-chain verification over `events.ndjson` and annex hashes (automated, every build); completeness-rule violations — cross-check of published FCC opinions vs filed instruments (operator attestation, publicly challengeable). Violations append events; PROCESS is derived from the violation event set per the frozen filing-time vs conduct distinction. **Correct OUTCOME coexisting visibly with PROCESS=VIOLATED:** the two fields are independent in the envelope, rendered side by side on the instrument (fixture C's exact shape), and counted in independent aggregates — the architecture has no code path by which one can suppress the other.

## 13 · CORRECTIONS SYSTEM
`record/corrections/fcc-corrections.ndjson` — append-only, Dossier's proven discipline reused as *pattern*, records fully decoupled (separate repo, separate log, separate snapshots; cross-references are public URLs only). Entry: `{correction_id (FCC-C-###), class: evidence-defect | invalidation | process-violation | challenge-resolution-miss | firewall | suspension | halt | kill | gate-transition | amendment, affected_refs (instrument/filing/identity ids), trigger, evidence, annex_refs, entered_at}`. Relationship to annexes: an instrument-touching correction always pairs with a correction-reference annex on that instrument, so both records point at each other. Snapshot cadence — **RATIFIED (D-8): full-record snapshot hashed + OTS-anchored on every kill, gate, and halt event, plus monthly.**

## 14 · AGGREGATES / PUBLIC METRICS
Every public metric is mechanically derived from raw records by one build script: terminal counts per disposition; hit-rate per frozen §L3 (TRIVIAL excluded, concessions as misses); VOID numerator / denominator / absolute count (never percentage alone); INVALIDATED count + informational-outcome count; TRIVIAL tally; DISPUTED count; PROCESS-violation rate over all instruments; anchored-precedence share; abandonment count; challenge counts and results incl. FCC challenge-resolution misses. Output lands in `derived/stats.json`, labeled DERIVED with the generating commit and recompute instructions. **No stored aggregate is a source of truth:** CI recomputes from raw records on every build and fails on any mismatch, and the verifier recomputes independently. Hand-editing a derived file is therefore both pointless and self-announcing.

## 15 · VERIFICATION TOOLING — flagship feature
One verification core library implementing: RFC 8785 canonical-byte reconstruction, SHA-256 comparison, locked-body integrity, annex hash + event-chain order verification, ordering-evidence level justification (is ANCHORED actually earned?), resolution-source reading re-execution, terminal-disposition re-derivation, OUTCOME/PROCESS recomputation, aggregate recomputation. Consumed two ways — **both, by design**: a CLI verifier in `/tools` (full verification including OTS proof checking against the verifier's own Bitcoin node or public calendars — the maximal-independence path), and later a browser verifier page (gated with the site build) doing bytes/hash/chain/scoring verification in-browser via WebCrypto, with OTS verification documented as the CLI/node path (browser-side full Bitcoin verification is not honest to promise; the page says so and links the proof + instructions). The §3 second-language implementation doubles as the parity oracle: CI requires CLI, second-implementation, and aggregates-builder agreement on every fixture and every real instrument.

## 16 · SECURITY / THREAT MODEL (Stage 0)
Format: ATTACK → IMPACT → PROTECTION → RESIDUAL TRUST.
1 Operator rewrites local git history → record falsified → force-push protection; multi-witness Layer-1 (second witness outside the repo); OTS anchors; public clones → residual: the pre-publication window only (nothing public exists to falsify there).
2 Compromised GitHub account/host → history tampering or deletion → OTS proofs survive independently; second witness survives; public GitLab mirror with independently scoped mirror credentials (RATIFIED D-9) + verifier detects hash breaks → residual: availability disruption, not undetectable falsification.
3 Compromised Netlify/deploy → site renders lies → the site is a projection; truth is repo + proofs; instrument pages display hashes and link the verifier → residual: users who never verify trust the rendering (mitigated by making verification a headline feature).
4 AI output substitution → adversary annex weakened → annex hash at publication; SAP versioning + input_sha256; supplements-only correction rule → residual: pre-publication generation trust (vendor bias disclosed via metadata; human supplements can add what the AI missed).
5 Challenge receipt deletion → challenge suppressed → global receipts log in git history; challenger holds their own receipt copy; second witness → residual: near-zero for deletion; suppression shifts to "never admit," countered by the submitter's receipt being publicly presentable.
6 Identity takeover → reputation hijack → wallet: key possession (user opsec); account: host auth; linking requires both sides → residual: user-side key/account security, disclosed.
7 Forged annexes → fake record content → annexes enter only via operator-signed pipeline events, hash-chained → residual: **Stage-0 operator trust at annex admission** — honest, disclosed, bounded by receipts + witnesses + the corrections obligation; this is the largest residual and is stated as such.
8 Duplicate IDs → record confusion → CI uniqueness gate across all id namespaces → residual: none meaningful.
9 Clock manipulation → false ordering → the layer model exists for this: FCC clocks are Layer 0 claims; PUBLISHED is host-attested; only ANCHORED is proof → residual: the publication-to-anchor interval is attestation-grade, permanently labeled as such.
10 OTS failure → precedence weakened → frozen §3.5 procedure; multi-calendar stamping; re-anchor; permanent labeling → residual: affected intervals are Layer-1 only, and say so.
11 Source disappearance → unresolvable criteria → fallback sources at lock; frozen VOID rules + anti-convenient-VOID protections; archived raw readings for already-resolved instruments → residual: genuine VOIDs happen; the 10% review trigger watches the rate.
12 Malicious user payloads / XSS → rendering compromise → raw storage escaped at render; strict CSP; no execution of user-supplied content anywhere; challenge bodies treated as text, never HTML → residual: standard web-surface diligence at the (later) site gate.
13 Schema/version confusion → misvalidation → `schema_version` + `doctrine_version` inside locked bytes; validators pinned per version; version-mismatch = lint failure → residual: none meaningful.
14 Race conditions at LOCK → double-assignment/partial state → single-operator pipeline with an exclusive lockfile; ids assigned before publication; atomic publish step → residual: none meaningful at Stage-0 scale.
15 Operator accidentally publishes an incomplete lock → malformed public artifact → pipeline publishes only after dual-canonicalization + hash + schema success (atomicity); if it happens anyway, the artifact is publicly hash-broken by construction → disclosed via corrections + INVALIDATED-BY-DOCTRINE where a defective pre-registration escaped → residual: embarrassment, on the record — which is the system working.
**Cryptographic vs operational trust:** cryptographically protected — locked-body integrity, annex/event hash chains, anchor upper bounds, wallet signatures. Operational trust (disclosed, bounded, watched) — annex admission and challenge resolution honesty (bounded by receipts, witnesses, the dismissed-challenge-vindicated rule, and corrections obligations), source-reading honesty (bounded by archived raw responses + recomputability), Layer-1 host attestation (bounded by multi-witness + anchoring).

## ADVERSARIAL RE-RUN — THE THREE CORRECTED FAILURE BOUNDARIES
**Boundary 1 · the commit point.** (a) *Operator publishes the hash to Telegram, regrets the instrument, deletes the post and reissues different bytes* → the (id, hash) binding became permanent at first witness success; deletion is detectable (channel archives, subscribers, the pipeline's own logged publication attempt), the earliest-publication-wins rule makes the reissue an integrity incident, and unproducible earliest bytes terminate the instrument INVALIDATED-BY-DOCTRINE → residual: a witness-only publication deleted before any third party observed it — a short, disclosed window, shrunk by pushing git immediately and surfacing `witness-degraded` states in telemetry. (b) *Send-but-unconfirmed witness publication* → treated as possibly-published; the pipeline must reconcile before any further publication for that id and never issues a second hash while unresolved → residual: operator diligence, telemetry-visible. (c) *Race producing two hashes for one id* → earliest wins deterministically; corrections entry mandatory → residual: none that the record hides. (d) *Git-first-fails path abused to claim "it was never really locked"* → the rule is witness-agnostic: the Telegram publication instant locked it, and the repo catching up later changes nothing → residual: none.
**Boundary 2 · bytes and chains.** (a) *EOL/encoding corruption on checkout breaks hashes* → `.gitattributes` policy + cross-OS CI byte-equality job + verifier reads raw blob bytes, never the working tree → residual: none meaningful. (b) *NDJSON line insertion/reorder/removal* → per-object RFC 8785 hash chain with `prev_event_sha256` inside the canonicalized object; any tamper breaks every subsequent hash; instrument chains root at `lock_sha256` so a chain cannot even be transplanted between instruments → residual: none. (c) *Canonicalization divergence between implementations on event objects* → the dual-implementation parity requirement extends to every event hash, CI-enforced → residual: none. (d) *Framing corruption of a log file* → semantic hashes live in the objects; the file is repairable from parsed objects without evidentiary loss, with the repair itself a visible commit → residual: none.
**Boundary 3 · receipts.** (a) *Provisional issued, public receipt never published (suppression)* → the challenger holds a signed provisional verifiable by anyone against the published intake key; its existence plus absence from `receipts.ndjson` is publicly demonstrable suppression/failure → an FCC process violation + corrections entry; suppression has no silent path → residual: FCC can be *shown* to have suppressed — which is the design, not a gap. (b) *Forged provisional by a malicious claimant* → signature verification fails without the intake key → residual: none. (c) *Intake key compromise* → key rotation via `governance/keys/` with versioned keys; every receipt names its `intake_key_version` and old receipts verify against old published keys; compromise disclosure is a corrections entry → residual: receipts signed during an undetected compromise window, bounded by rotation and disclosure. (d) *Queue loss between provisional and publication* → durable queue + telemetry pending count + resubmission honored with dedupe by `challenge_content_sha256`, and first-filer ordering pinned to the provisional `received_at` — so neither loss nor delay can reassign first-filer credit or erase intake → residual: none that the challenger cannot prove.
